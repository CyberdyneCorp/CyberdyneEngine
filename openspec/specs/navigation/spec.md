# navigation Specification

## Purpose

Defines navigation: navigation mesh generation, pathfinding, path smoothing, dynamic obstacles,
local avoidance, off-mesh links, and the agent components gameplay uses.

## Requirements

### Requirement: Navigation mesh
A **navigation mesh** SHALL be a set of convex polygons with adjacency, each carrying an area type
and a traversal cost, organised into **tiles** so regions can be rebuilt independently.

Navigation meshes SHALL be generated by voxelising source geometry and extracting walkable
surfaces, parameterised by: cell size and height, agent radius, height, maximum climb, and
maximum slope; region minimum and merge sizes; edge maximum length and error; and detail sample
distance and error.

Generation SHALL support filtering by layer, by tag, and by an explicit include/exclude volume.

#### Scenario: Agent radius erodes the mesh
- **WHEN** the agent radius is 0.5 m
- **THEN** the walkable surface SHALL be shrunk by that distance from obstacles, so a path's
  centre line is always traversable

#### Scenario: Tile rebuild
- **WHEN** geometry changes within one tile
- **THEN** only that tile SHALL be rebuilt, with neighbouring tiles' adjacency updated

#### Scenario: Multiple agent sizes
- **WHEN** a project has agents of different radii
- **THEN** a separate navigation mesh SHALL be generated per agent profile, selectable per agent

### Requirement: Runtime mesh updates
Navigation meshes SHALL support runtime modification through: tile rebuilds from changed
geometry, and **navigation obstacles** that carve or mark areas without a full rebuild.

Rebuilds SHALL run on job workers and be published atomically, so queries always see a consistent
mesh.

#### Scenario: Door opens
- **WHEN** a door's collision changes
- **THEN** the affected tiles SHALL be rebuilt asynchronously and swapped in, with in-flight
  queries completing against the previous version

#### Scenario: Dynamic obstacle
- **WHEN** a crate is dropped
- **THEN** it SHALL mark its footprint as unwalkable through an obstacle rather than triggering a
  voxelisation rebuild

### Requirement: Pathfinding
Path queries SHALL run **A\*** over the polygon adjacency graph with a Euclidean heuristic,
producing a **corridor** of polygons, then a point path.

Queries SHALL support: area cost multipliers per agent (so an agent can prefer roads or avoid
water), an area mask excluding types entirely, a maximum search node budget, and partial paths
when the target is unreachable.

Queries SHALL be issuable synchronously and asynchronously, and SHALL be safe from parallel
systems.

#### Scenario: Unreachable target
- **WHEN** no path exists
- **THEN** the query SHALL return the reachable point closest to the target, flagged as partial,
  rather than failing silently

#### Scenario: Area preferences
- **WHEN** an agent has a high cost for "water" areas
- **THEN** A* SHALL route around water unless the detour exceeds the cost difference

#### Scenario: Search budget exceeded
- **WHEN** a query exceeds its node budget
- **THEN** it SHALL return the best partial path found and report that the budget was hit

### Requirement: Path smoothing
Corridors SHALL be converted to point paths by the **funnel algorithm** (simple stupid funnel),
producing a taut string-pulled path.

Optional post-processing SHALL include: simplification within a tolerance, and a corner-radius
smoothing pass producing curved paths for vehicles.

#### Scenario: Straight line across open ground
- **WHEN** start and target lie on a large flat region crossed by many polygons
- **THEN** the funnel SHALL reduce the path to a straight two-point line

#### Scenario: Vehicle path
- **WHEN** corner smoothing is enabled with a turning radius
- **THEN** the path SHALL be rounded at corners so it is followable by a non-holonomic agent

### Requirement: Off-mesh links
The engine SHALL support **off-mesh links**: explicit connections between two points that are not
traversable through the mesh, such as jumps, ladders, doors, and teleporters.

Links SHALL carry: bidirectionality, a cost, an area type, an agent-capability requirement, and a
user-defined action tag that gameplay interprets.

#### Scenario: Jump link
- **WHEN** a path routes through a jump link
- **THEN** the path SHALL include the link's endpoints tagged with its action, and the agent's
  gameplay code SHALL perform the jump rather than walking

#### Scenario: Capability gating
- **WHEN** an agent lacks the capability a link requires
- **THEN** the link SHALL be excluded from that agent's search

### Requirement: Local avoidance
The engine SHALL provide **local avoidance** so agents following paths do not collide with each
other or with moving obstacles, using a reciprocal velocity obstacle formulation.

Agent parameters: radius, height, maximum speed, neighbour distance, maximum neighbours, time
horizon for agents, and time horizon for obstacles.

Avoidance SHALL compute a **desired velocity adjustment**, not a position: the agent's controller
remains responsible for movement and for physics collision.

#### Scenario: Head-on agents
- **WHEN** two agents approach each other
- **THEN** each SHALL receive an adjusted velocity steering around the other, with reciprocity
  preventing oscillation

#### Scenario: Avoidance is advisory
- **WHEN** avoidance produces a velocity
- **THEN** the agent's controller SHALL still perform physics movement, and avoidance SHALL NOT be
  relied on to prevent interpenetration

#### Scenario: Crowd scaling
- **WHEN** hundreds of agents are active
- **THEN** avoidance SHALL run as a parallel system with spatial partitioning to bound neighbour
  queries

### Requirement: Navigation components
Navigation SHALL be exposed as components:

| Component | Role |
|---|---|
| `NavMeshSurface` | Declares a region whose geometry contributes to a navigation mesh |
| `NavAgent` | An agent: target, path, speed, avoidance parameters, capabilities |
| `NavObstacle` | A dynamic obstacle carving or marking the mesh |
| `NavLink` | An off-mesh link |
| `NavArea` | Marks a volume with an area type and cost |

`NavAgent` SHALL expose: set target, current path, next path point, distance to target, path
status (idle, computing, following, arrived, failed), and events for path completion and failure.

#### Scenario: Agent repaths on mesh change
- **WHEN** the navigation mesh version changes and an agent's corridor is invalidated
- **THEN** the agent SHALL recompute its path automatically, subject to a repath rate limit

#### Scenario: Agent arrival
- **WHEN** an agent reaches its target within the arrival distance
- **THEN** its status SHALL become arrived and an event SHALL be emitted

### Requirement: Multiple navigation worlds
The engine SHALL support multiple independent navigation worlds — for different agent profiles,
different floors of a building, or entirely separate simulation contexts — each with its own
meshes, agents, and obstacles.

#### Scenario: Flying and walking agents
- **WHEN** a project has both walking and flying agents
- **THEN** they SHALL use separate navigation worlds with different generation parameters, or the
  flying agents SHALL use a different navigation strategy entirely

### Requirement: 2D navigation
Navigation SHALL support 2D through the same polygon and pathfinding machinery operating on a
plane, with navigation polygons generated from 2D collision geometry and tilemap data.

#### Scenario: Tilemap navigation
- **WHEN** a tileset declares per-tile navigation polygons
- **THEN** the tilemap SHALL contribute them per chunk, and the navigation mesh SHALL be rebuilt
  per chunk on cell changes

### Requirement: Navigation debugging
The engine SHALL provide debug visualisation of: navigation mesh polygons coloured by area type,
tile boundaries, polygon adjacency, off-mesh links, agent paths and corridors, avoidance
velocities and neighbour sets, and obstacle footprints.

Statistics SHALL include: query counts and timings, path lengths, repath rates, and tile rebuild
times.

#### Scenario: Diagnosing a failed path
- **WHEN** an agent cannot reach an apparently reachable target
- **THEN** the polygon and adjacency visualisation SHALL reveal the disconnected region or the
  eroded gap
