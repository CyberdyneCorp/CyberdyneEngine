# `tests/render/`

Golden-image rendering tests: fixed scenes, a fixed camera, deterministic settings, compared against
committed reference images with a perceptual metric and a per-test tolerance. Budget: 5 s per test.

It was **empty until M3**, the milestone that lands the render graph and the first backend: there was
nothing to photograph before then, and a reference image generated by a renderer that does not exist
is not a reference.

## What is here now — `render.conventions`

The first suite is not a golden-image suite. It is section 5 of the M3 tasks: **the conventions,
asserted on a device**.

| Case file | Asserts |
|---|---|
| `test_reversed_z.cpp` | the depth buffer clears to 0, the near plane maps to 1 and the far plane to 0 **as sampled back from the device**, depth is monotonic in distance, the nearer surface wins whichever order the two are drawn in, and an infinite far plane keeps depth in `[0, 1]` without reaching 0 |
| `test_camera_relative.cpp` | a scene one million units from the origin renders **bit-identically** to the same scene at the origin — plus the control, which shows the world-space path losing the detail the camera-relative one keeps |
| `test_axis_conventions.cpp` | −Z forward, +X right, +Y up and right-handedness, checked against the rendered image rather than only against the arithmetic — which is what catches a wrong viewport Y flip |

`probe.h` / `probe.cpp` are the shared fixture: a device, one pipeline, and a frame through the render
graph that hands back the colour target as texels and the **depth target as depths**. Every assertion
is on a number copied off the device.

**Why not a golden image.** design.md §3: "A golden image is not sufficient evidence — a scene can
look right with an inverted comparison until something intersects." Golden images are task 6.3's and
they answer "does the frame look right"; these cases answer "is the depth comparison the right way
round", which a picture cannot.

The suite is **declared only when a rendering backend is compiled in**, and **skips loudly** on a
machine that has one and no GPU, naming the backend that was selected instead. `shaders/` holds the
Slang probe and its checked-in SPIR-V, compiled offline by `shaders/embed_spirv.py` for the same
reason the shader suite's fixtures are: a render suite must run in a build with no shader compiler,
and `CY_SHADER_SLANG` is off in Profile and Shipping and can be turned off anywhere.

## The golden images — `render.golden`

Task 6.3. **What is photographed is the milestone's artefact.** These cases render
`samples/03-first-light`'s frame, reached through `cy::sample-first-light` — the library half of the
sample — rather than a scene written for a test. A golden suite with a scene of its own drifts from
the sample inside a milestone, and its references are then photographs of something nobody ships.

| Case | Asserts |
|---|---|
| the scene | the frame matches `references/first_light.png`, with zero validation errors and the five passes the sample declares |
| the scene at 10<sup>6</sup> | it matches **the same reference file**. Not "close to": camera-relative rendering means the image is the same one, which is tasks 5.3 and 7.5 |
| the sun's shadow off | it matches a *different* reference, **and** the two references differ. Without that control, a frame that had quietly stopped sampling the shadow map would pass the first two cases forever |
| the null backend | the same frame through `cy::rhi-null`, compared to the device's structure for structure — passes, culls, submits, barriers, batches, ownership transfers, draws and triangles |
| the frame after the ring turns | the same frame rendered `2 × frames_in_flight + 1` times still matches `references/first_light.png`. This is the regression case for the recycled-descriptor defect described below, and it is here rather than in `render.frames` because it is the one multi-frame claim that needs a committed image |

**The tolerance is derived, not tuned.** `golden.h` carries the argument in full; in short:

* A texel differs when any channel differs by more than **two** 8-bit steps. The target is
  `Rgba8Unorm` and the shader's last operation is `pow(x, 1/2.2)` before the hardware quantises to
  1/255, so one step is the physical difference two conformant implementations can produce and two
  is one step of headroom over it. Three is a shading difference.
* A texel may differ **only where the reference itself has a high-contrast four-neighbour**. That
  count is measured off the committed reference — an implementation-independent property of the file
  — and is the budget. A minified checkerboard's sampled texel can flip between two greys on the
  last bit of a UV; nothing away from such an edge can. `differing_off_edge` must be zero, and it is
  the assertion a regression trips first.
* On the machine the reference came from, `differing` is **zero**, and the case says so separately.

**The difference is inspectable in review.** A failing case writes `<name>-difference.png` into the
suite's working directory: the reference at half intensity with every differing texel in magenta.
The references and the diffs are PNGs so that a reviewer sees them in a browser; the encoder writes
**stored (uncompressed) deflate blocks**, which every viewer reads and which costs about 1.3× the
raw pixels — 62 KiB a reference at 192×108. The decoder reads only what the encoder writes, and
rejects a reference re-encoded by another tool with a message saying so.

**Regenerating a reference is a deliberate, reviewed step**, which is `testing-and-quality`'s
requirement:

```
CY_RENDER_UPDATE_GOLDEN=1 ctest -R render.golden
```

writes each reference, prints its path, **and fails**. Failing is the mechanism: a mode that
regenerated and then passed would let a run with that variable set in its environment launder a
defect into the repository. Look at what it wrote, then commit it.

## Many frames on the device — `render.frames`

**M4 task 1.3, and it exists because of what M3's suites could not see.** Every device suite M3
shipped rendered exactly one frame. That is how this reached the artefact:

> `VulkanDevice::allocate_descriptor_set(layout, per_frame)` took the flag, recorded it, and then
> allocated from the **current frame's** pool whichever value it had — and a frame pool is reset the
> moment its slot comes round. A set the caller asked to be persistent was recycled after
> `frames_in_flight` frames, and from that frame on every draw bound a `VkDescriptorSet` the driver
> had already destroyed: **24 validation errors a frame from frame 3, on a run that still printed
> "exit 0 (clean)"**.

A one-frame suite cannot see a defect that begins at frame 3. Neither can a many-frame suite that
looks at the error total afterwards without ever asking *which* frame broke.

| Case | Asserts |
|---|---|
| validation stays clean over many turns of the ring | `frames_in_flight × 8 + 1` frames, each with a **different camera** so the per-frame uniform ring and descriptor pools genuinely turn over; validation is read **after every frame**, and the case reports the **first** frame at which it spoke. It also asserts the derivation does not change shape between steady-state frames — submits, passes, culls, barriers, batches, ownership transfers, transient bytes, `plan_hash`, draws and triangles — and that the upload pass is present on the first frame and absent afterwards, which `render.null_frame` asserts with no GPU and nothing asserted on one |
| the frame at the end of a long run is bit-identical to the first | phase 0 captured before the orbit and again after it, compared **exactly**. No reference file and no tolerance: a descriptor that had quietly stopped naming the shadow map trips no validation layer, so silence is not the whole claim |
| the orbit does change the image | the control. Without it, the case above would pass just as happily on a renderer that ignored the camera |

**It compares the run against itself.** That is deliberate: nothing here can be laundered by
regenerating a golden image, and "bit-identical" is a stronger claim than "within the tolerance".
`device.h` is the shared fixture — a device with validation and **synchronisation** validation on,
and a cumulative error count a case can read after each frame — and `render.golden` uses it too.

The suite costs about half a second on an RTX 5060 and is declared, like the other device suites,
only when `CY_RENDERER_VULKAN` is on; it skips loudly with no GPU.

## The same frame with no GPU — `render.null_frame`

Task 6.4, and it matters more than the golden images. `render.golden`, `render.conventions` and
`render.frames` need a device and are not even declared without a backend; **this suite is declared
always**, runs on
every pull request on every platform, and checks the part of a frame that is decided rather than
drawn.

| Case | Asserts |
|---|---|
| the frame runs with no GPU at all | five passes, no culls, one submit, no ownership transfers, two draws per object, two rendering scopes, one copy each way |
| every barrier in the stream is the graph's | the number of barrier batches in the recorded command stream **equals** the number the compiled plan derived. The grep gate (task 2.2.4) says no barrier *symbol* exists outside the graph; this says no barrier *command* reached the stream from outside it |
| the same frame twice records the same stream | identical `plan_hash` and identical `command_log_hash` — task 7.6, and design.md §6's deterministic submission |
| the upload pass exists once | five passes on the first frame, four afterwards, and fewer barriers on the second: an absent pass rather than a branch |
| aliasing | the plan's `transient_bytes` never exceeds its unaliased figure. This frame's two transients overlap in time and therefore cannot alias, and the case says so rather than claiming a saving it did not make |

A rendering milestone whose only gate is a photograph is a rendering milestone that is not gated on
the machines that build it.

## What M3 did NOT wire here, from `testing-and-quality`

Recorded rather than quietly dropped. The first two are done and the rest are not, and none of them
has a milestone against it yet:

- **done** — a per-test tolerance and a difference metric, with the diff inspectable in review
- **done** — regeneration of references only through a deliberate, reviewed step
- **not done** — a run against every enabled RHI backend, recording which backend produced a
  failure. There is one backend that draws; `render.golden`'s fourth case compares Vulkan's frame
  structure against the null backend's, which is the shape a parity check will take when Metal
  arrives at M7
- **not done** — converged-mode capture for temporally accumulating illumination. There is no
  temporal accumulation before M7
- **not done** — reference comparison against the offline path tracer, reporting error rather than
  asserting equality. There is no path tracer

## The deferred XR seams — wired at M3

`xr-support` is deferred, and `delivery-roadmap` requires deferred scope to carry its re-entry
point: the milestone at which it is reconsidered, the seams that must stay open until then, and the
**check that proves those seams are still open**. XR is reconsidered at M11; without these three
checks the seams close silently, and the first evidence is an XR port that turns out to be a
renderer rewrite.

The three entries below are that check list. They are recorded here, at the milestone that created
the directory, because the renderer they test lands at M3 and a note in a closed change is not a
gate. Each names what it asserts, the requirement it comes from, and what closing the seam would
cost.

| Test | Asserts | Prerequisite | If the seam closes |
|---|---|---|---|
| `test_multi_view_single_submission` | A camera with two views submits its geometry **once**, amplified across both layers, with per-view projection and transform matrices indexed in the shader. Two passes over the same geometry fail the test even when the images match. | `xr-support` — Multi-view rendering prerequisite; `rendering-forward-clustered` | Stereo becomes a second full render of the scene, and every pass written in between assumed one view per camera |
| `test_runtime_driven_frame_timing` | One `tick()` runs one frame against an **externally supplied** predicted display time, and the frame's timing derives from that argument rather than from the engine's own clock. Reads of a global clock inside the frame fail it. | `xr-support` — Runtime-driven frame timing prerequisite; `core-platform-abstraction` | The engine owns the loop again, which is the M6 restructure `design.md` §3 exists to avoid |
| `test_late_latched_view_matrices` | A view transform updated **after culling and command recording have begun** reaches submission, with no draw command re-recorded. The view matrices come from a buffer written late in the frame. | `xr-support` — Late-latching prerequisite | View matrices bake into recorded commands, and head-pose latency becomes a property of the whole render graph |

The middle seam is the one already load-bearing: `Runtime::tick()` exists from M0 and the host owns
the loop, so an M0 test already asserts that half. What M3 adds here is the frame *time* arriving
as an argument rather than being read from a clock — the half a renderer can violate.

### They exist now — `render.xr_prerequisites`

Task 6.5. All three run on the **null backend**, because all three are questions about structure
rather than about pixels, and the null backend records every command and hashes the stream. They are
declared always and run wherever the engine builds.

| Case | How it is checked | What would fail it |
|---|---|---|
| two views are one submission | one `begin_rendering` with `layer_count == 2` and a two-bit `view_mask`, and exactly **one** draw inside it; plus `Capability::Multiview` queried rather than assumed | a renderer that looped over the eyes: two scopes and two draws, even with a correct image |
| the frame's inputs are arguments, not a clock | the same camera rendered twice, with three frames of other work in between, produces a **byte-identical** command stream and the same plan hash | anything animated from a clock of its own — a jitter sequence, a temporal index, a time of day — which would hand an XR runtime a frame for some other instant than the predicted one |
| the view reaches submission through memory | two orientations from the same eye record an identical stream, **and** every push constant in the frame is exactly the 64-byte object block, so the view-projection is not in the command stream at all; it is in the descriptor-bound uniform buffer a late write can replace. The control: a different object count does change the stream | a renderer that put the view-projection in the push block — its pushes would be 128 bytes |

**The second seam is HALF OPEN and this is the record of it.** The half checked above is the
renderer's: no clock reaches the frame. The half that is *not* open is `cy::Runtime::tick()`, which
takes no predicted display time — a host can call it once per frame but cannot yet tell it when the
frame will be displayed. Adding that argument is small today and gets expensive once anything
downstream reads the runtime's clock instead. It is named here, in the case's own comment, and in
`tools/roadmap/milestones/m3.toml`'s notes; it is not asserted away.

Bringing XR forward, or closing any of these seams deliberately, is an OpenSpec change against
`xr-support` and `delivery-roadmap`, not a decision taken inside a render pull request.

**Governed by**: `testing-and-quality`, `xr-support` (deferred prerequisites), `rendering-*`.
