# `tests/render/`

Golden-image rendering tests: fixed scenes, a fixed camera, deterministic settings, compared against
committed reference images with a perceptual metric and a per-test tolerance. Budget: 5 s per test.

**Empty until M3**, the milestone that lands the render graph and the first backend. There is
nothing to photograph before then, and a reference image generated by a renderer that does not exist
is not a reference.

What M3 wires here, from `testing-and-quality`:

- a per-test tolerance and a perceptual difference metric, with the diff inspectable in review
- a run against every enabled RHI backend, recording which backend produced a failure, since backend
  parity is itself a requirement
- converged-mode capture for temporally accumulating illumination, failing when a scene does not
  converge within its frame cap rather than capturing an unstable image
- reference comparison against the offline path tracer, reporting error rather than asserting
  equality, so a regression in the real-time approximation is measurable
- regeneration of references only through a deliberate, reviewed step

## The deferred XR seams — wired at M3

`xr-support` is deferred, and `delivery-roadmap` requires deferred scope to carry its re-entry
point: the milestone at which it is reconsidered, the seams that must stay open until then, and the
**check that proves those seams are still open**. XR is reconsidered at M11; without these three
checks the seams close silently, and the first evidence is an XR port that turns out to be a
renderer rewrite.

The three entries below are that check list. They are recorded here, at the milestone that created
the directory, because the renderer they test lands at M3 and a note in a closed change is not a
gate. Each names what it asserts, the requirement it comes from, and what closing the seam would
cost.

| Test | Asserts | Prerequisite | If the seam closes |
|---|---|---|---|
| `test_multi_view_single_submission` | A camera with two views submits its geometry **once**, amplified across both layers, with per-view projection and transform matrices indexed in the shader. Two passes over the same geometry fail the test even when the images match. | `xr-support` — Multi-view rendering prerequisite; `rendering-forward-clustered` | Stereo becomes a second full render of the scene, and every pass written in between assumed one view per camera |
| `test_runtime_driven_frame_timing` | One `tick()` runs one frame against an **externally supplied** predicted display time, and the frame's timing derives from that argument rather than from the engine's own clock. Reads of a global clock inside the frame fail it. | `xr-support` — Runtime-driven frame timing prerequisite; `core-platform-abstraction` | The engine owns the loop again, which is the M6 restructure `design.md` §3 exists to avoid |
| `test_late_latched_view_matrices` | A view transform updated **after culling and command recording have begun** reaches submission, with no draw command re-recorded. The view matrices come from a buffer written late in the frame. | `xr-support` — Late-latching prerequisite | View matrices bake into recorded commands, and head-pose latency becomes a property of the whole render graph |

The middle seam is the one already load-bearing: `Runtime::tick()` exists from M0 and the host owns
the loop, so an M0 test already asserts that half. What M3 adds here is the frame *time* arriving
as an argument rather than being read from a clock — the half a renderer can violate.

Bringing XR forward, or closing any of these seams deliberately, is an OpenSpec change against
`xr-support` and `delivery-roadmap`, not a decision taken inside a render pull request.

**Governed by**: `testing-and-quality`, `xr-support` (deferred prerequisites), `rendering-*`.
